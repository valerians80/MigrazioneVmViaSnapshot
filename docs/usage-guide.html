1. What it does and does not do

Invoke-VmSkuMigration.ps1 moves one Azure VM at a time to a new size (for example Bv1 → Bsv2, Fsv2 → Dlsv6) by rebuilding it from snapshots, as described in the size conversion playbook. It works on Azure only: it never goes inside the guest operating system and it never deletes anything.

In short: it shuts the VM down, snapshots every disk, creates a new VM with the -mig suffix that takes over the same private IP (and the public IP, if there is one), and leaves the original VM switched off and untouched. If something goes wrong, the rollback brings the original VM back in a few minutes.

The script handlesLeft to you (the script lists it before it starts)
  • New VM: chosen size, zone, security type, generation, license (Hybrid Benefit), tags, marketplace plan
  • Disks: new disks from full snapshots, same SKU, size, zone, LUN and caching
  • NIC(s) with the original private IP (static), NSG, ASG, accelerated networking, DNS
  • Original public IP: detached from the old NIC and attached to the new one
  • Automatic checks on the Azure side
  • Rollback
  • Backup: the new VM is not protected, you enable it by hand after validation
  • Extensions: none is installed, the old VM's list is shown
  • Managed identities (system and user-assigned), role assignments, Key Vault policies
  • Load balancer, application gateway, NAT rules
  • Availability set and proximity placement group
  • Locks, DCR associations (monitoring), capacity reservation
  • DNS, firewall, allow-lists and every check inside the VM
  • Deleting the old VM, its NIC, disks and snapshots
Backup and extensions
Both are written in yellow on the very first screen, in the manual checks and in the "not handled" list you must acknowledge before the deployment: no surprise at the end.

2. Before you start

Requirements

  • PowerShell 7 (the pwsh command) and the modules Az.Accounts, Az.Compute, Az.Network, Az.Resources. If something is missing the script says so immediately and does nothing else.
  • Permissions: Contributor on the resource groups of the VM, of the network and of the disks.
  • MFA: if the tenant requires it for changes, see the dedicated paragraph (section 5): the script handles it.
  • A wide window: the two columns need about 110 characters. In a narrower window the two blocks are stacked.
  • Always the same folder: the script writes its state to .\migration\<VM name>\ relative to the folder you launch it from. To resume or roll back, launch it again from the same folder (or with -WorkRoot).

Starting it

.\Invoke-VmSkuMigration.ps1

Everything is asked on screen; the parameters are optional and only skip questions.

ParameterEffect
-TenantIdSigns in to that tenant (otherwise Connect-AzAccount decides)
-SubscriptionIdSkips the subscription list
-VmNameSkips the question about the VM name
-ResourceGroupNameSkips the VM lookup (use together with -VmName)
-WorkRootFolder that holds one sub-folder per VM. Default: .\migration
-SuffixSuffix of the names the script creates. Default: -mig
-RequireMfaSigns in right away with a fixed MFA request (context p1), before any change (forces a new sign-in). The value comes from the error of one tenant and is not guaranteed for every tenant: use -ClaimsChallenge there
-ClaimsChallengeSame as -RequireMfa but with the value Azure printed in its own error message (base64 or JSON)

The map between current and new sizes is at the top of the script ($script:SkuMap) and is edited there.

3. The walkthrough, screen by screen

The path is single and guided. The examples use a fictitious VM srv-app01 (Standard_B2ms, two data disks, a public IP). Long lines wrap as they do in the console.

How to read the two-column screen

  • Green, on the left: the current VM, with its state (RUNNING / DEALLOCATED (off)).
  • Red, on the right: the new VM, with its state (NOT CREATED YET / RUNNING).
  • Fields: resource group, name, size, security type, public IP, NICs with IPs, OS disk, data disks with LUN, extensions.

4. When the script stops before starting

Everything that happens up to the final Y/N is read-only. If the script stops in this phase it prints Nothing was changed in Azure: fix the cause and run it again, it starts from scratch.

SituationWhyWhat to do
VM not migratableUnmanaged or ephemeral OS disk, scale set member, Ultra SSD enabled, confidential security type, Azure Disk Encryption, shared disk, Ultra/PremiumV2 disk, IPv6 configurationHandle the VM separately: the script does not touch it
No usable sizeSize not offered or restricted in the region/zone, vCPU quota too low, generation not supported, vCPU or memory would be reducedAsk for quota or pick another region/zone; for Gen1 convert the disk
No free IPThe subnet has no free address to use as a placeholderFree an address and run again
Names already in useVMs, NICs, disks or snapshots with the -mig names already existRemove them or roll back the earlier attempt
Manual checks not confirmed / ACKNOWLEDGE not typed / N at the deployment questionThe operator chose not to go onNothing: no change was made

5. Interruptions, MFA and resume

The deployment is checkpointed: after every step the state is saved to disk. An error, a closed window or a network failure do not lose the work already done.

Window closed in the middle of a step
That step is run again on resume. If Azure answers that the resource already exists, read the message: it normally ends with a rollback and a new attempt.
Before resuming
Understand the cause of the error. Resuming without having solved it repeats the same error. While the deployment is interrupted the original VM may already be off: do not start it by hand if the new one exists and is running.

6. A VM already migrated: re-check and rollback

Running the script again on the name of a VM that already has a migration in progress or completed (from the same folder) does not start over: it shows the state and offers a menu.

SituationMenu options
Deployment interruptedR resume · B rollback · Q quit
Deployment completedV re-check · B rollback · Q quit
After a rollbackNo menu: the state is cleared and a new run starts from scratch

What the rollback does and does not do

It doesIt does not
  • Stops and deletes the new VM and its NICs (freeing the IPs, the public one included)
  • Gives the original NIC its private IP back (with the previous allocation type) and its public IP
  • Starts the original VM, after checking that the new one is off
  • On request, deletes the new disks and snapshots (needed to redo the migration with the same names)
  • Clears the state: you can start again from scratch
  • Does not undo what was done by hand on the new VM (identity, load balancer pools, backup, extensions, DNS, firewall): the final checklist reminds you
  • Does not touch the original VM except to bring it back as it was
  • Never deletes anything of the original VM
When it can be done
As long as the original VM and its resources exist. Since the script never deletes them, the rollback stays possible until you remove them yourself, after sign-off.

7. Work folder and files

For every VM the script creates a folder under migration (in the folder you launch it from, or under -WorkRoot).

C:\Migrations\                      <- the folder you launch the script from
  Invoke-VmSkuMigration.ps1
  migration\
    srv-app01\
      config.json                     snapshot of the VM before it was touched
      state.json                      progress, completed steps, placeholder IPs, rollback history
      migration.log                   timestamped history
      validation-report.csv           result of the automatic checks
FileContent and use
config.jsonEverything read from the VM before touching it: compute, disks and LUNs, NICs and IPs, extensions (name, type, version, state), identity, locks, the "not handled" list. The deployment, the checks and the rollback rely on it. It is your starting documentation.
state.jsonProgress: completed steps with date and time, placeholder IPs, resources created, confirmations given (who and when), rollback history with the reason. It is what makes resuming possible.
migration.logHistory of everything the script did, with warnings and errors. The complete errors (with the stack) are here, not on screen.
validation-report.csvOne check per row: area, check, expected value, found value, result (PASS, FAIL, WARN, INFO). Opens in Excel.

Do not delete the folder while a migration is in progress
Without it the script does not recognize the migration: it cannot resume or roll back in a guided way. Keep it until the change is closed. If the folder is synchronized by OneDrive, a locked file can cause errors: better to run the script from a local folder.

8. The automatic checks

At the end of the deployment (and when you choose V) the script compares the new VM with the snapshot of the configuration taken at the beginning. They are checks on the Azure platform: they look at nothing inside the VM.

AreaWhat is compared
VMRunning state; provisioning succeeded; chosen size; original VM not running (golden rule); zone; security type; license (Hybrid Benefit); boot diagnostics enabled; generation; tags
DisksCaching and SKU of the OS disk; number of data disks; for every LUN: name of the new disk, caching, size, SKU, zone
NICNIC attached to the VM; NSG; accelerated networking; DNS servers; for every IP configuration: private IP (must be the original), static allocation, public IP, ASGs; old NIC parked on the placeholder
Informational (INFO)The list of what stays manual; the boot diagnostics screenshot (if it cannot be downloaded, look at it in the portal: VM → Boot diagnostics)
  • FAIL: a real difference. Fix it or roll back.
  • WARN: look at it, it does not block.
  • INFO: information.

The checks do not say the VM works: they say Azure created what was planned. Whether the operating system and the application work is verified with the tests in the final checklist.

9. After the migration

  1. Keep the original VM switched off and test the new VM (checklist on screen and at the end of this guide). The original and the new VM share hostname, SID and Active Directory computer account: if both run, the trust can break and shutting one down does not repair it.
  2. Do by hand what is left on the new VM, from the list shown at the end: extensions (with their settings and keys), managed identity and roles, load balancer pools, availability set (it cannot be added after creation), DNS, firewall, monitoring.
  3. Backup: enable it on the new VM when the old one and its backup item have been dealt with. The restore points of the old VM cannot be transferred.
  4. Formal sign-off from the application owner.
  5. Clean-up by hand, only after sign-off and in this order: original VM → its NIC → (after the retention period, 14 days unless asked otherwise) original disks → snapshots. Before deleting the original VM check that its disks are not set to be deleted with the VM.
  6. Inventory: update size and configuration.
If something is wrong
The rollback is available as long as the original VM exists. After you delete the original VM there is no automatic way back.

10. Safety rules, the playbook and limits

The playbook golden rules and how the script applies them

RuleIn the script
Never two VMs running together (same hostname, SID, AD account)Before creating the new VM and before starting the old one in the rollback it checks that the other is off; otherwise it stops
Never delete disks or snapshots before sign-offThe script deletes nothing of the original VM. It only deletes what it created itself, and only in the rollback
The temporary disk is always lostManual checks at the start; the guest part (pagefile, tempdb, fstab...) stays with the team
Capture the configuration before changing anythingconfig.json is written before any change
One machine at a time until the procedure is provenThe script works on a single VM per run

Differences from the playbook

PlaybookScript
On-demand backup or snapshot as a rollback pointFull snapshots only (backup stays manual)
Explicit restore of Hybrid Benefit, tags, extensions, identity, backup, locksHybrid Benefit and tags are restored; the rest stays manual and is listed
Network: new NIC, original IP transferred, placeholder on the old oneSame; the placeholder is chosen automatically (first free IP of the subnet)
Validation: platform, guest, applicationThe platform part is automatic; guest and application stay with the team
RollbackGuided (section 6); manual actions are not undone
Decommissioning with locks and retentionNot in the script: done by hand after sign-off

Known limits

  • The script verifies that Azure created what is planned, not that the operating system boots and the application works. This, and in particular the start-up of a Gen1 VM on a v2 size, is checked in the tests.
  • The security type of the new OS disk is inherited from the snapshot (it cannot be set when copying): if it turns out different the script warns you.
  • The boot diagnostics of the new VM are always managed by Azure; the screenshot is looked at in the portal.
  • During the migration disks and snapshots exist twice: the storage cost doubles until the clean-up.
  • The script works on one VM at a time (reading the list from a file is a future evolution).
  • The rollback deletes the new VM: anything attached to it by hand has to be done again.
  • The first real cases must be done one at a time and checked thoroughly, as the playbook says, before going in series.

12. Operator checklist

Before

  • PowerShell 7 and Az modules ready
  • Permissions on the resource groups
  • Window at least 110 characters wide
  • Work folder chosen (always the same for this VM)
  • Guest manual checks done (temp disk, DHCP, clean reboot)
  • Owner informed, change window agreed
  • DNS, firewall and allow-lists noted for a possible rollback
  • VM extensions noted, with settings and keys
  • Backup: you know how you will enable it afterwards
  • Drive letters and mount points noted

During

  • Do not close the window
  • If it stops: read the message, do not rerun blindly
  • If MFA appears: complete it in the browser
  • Resume: same folder, choose R
  • Any doubt: roll back (B), as long as the original VM exists

After

  • Original VM kept off for the whole test phase
  • Zero FAIL in the checks
  • Guest and application tests done by the owner
  • Extensions, identity, load balancer, DNS, monitoring restored by hand
  • Sign-off obtained
  • Backup enabled on the new VM
  • Clean-up by hand: VM → NIC → disks → snapshots (after retention)
  • Inventory updated
